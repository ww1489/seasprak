## 1. 执行摘要

### 1.1 问题与方案

需要一套可以持续扩展的 Go Agent 底座，使编码助手和后续业务应用共用会话、任务执行、消息与事件机制。新增工具、技能或声明式工作流时，不应修改模型推理循环，也不应绑定特定 UI。

由 CreateAgentSession 组装运行对象，AgentSession 控制会话内任务，Agent 复用 Eino DeepAgent 执行，SessionManager 保存历史。资源发现与能力注册分别交给 ResourceLoader 和 ExtensionRegistry。独立建立 Go module，不修改、不依赖 `pigo/`。

### 1.2 可验证的成功标准（建议验收门槛）

以下是拟定的产品验收条件，不是现有实现的测试结果，也不是已承诺的上线日期。

| 编号 | 成功标准 | 验证方式 |
| --- | --- | --- |
| K-01 | SDK 能在没有终端交互、没有编码工具时完成一次带自定义工具的任务 | 使用可控假模型和一个内存计算工具，检查调用、结果及完成事件 |
| K-02 | 编码配置能完成读文件、修改一个限定文件、运行给定测试命令并报告结果 | 在临时示例仓库中核对 diff、命令退出码及最终报告；不得改动范围外文件 |
| K-03 | 增加一个工具、一个 skill、一个声明式工作流均无需改动 AgentSession 协调逻辑或 Agent 执行循环 | 三个扩展示例分别加载并完成各自验收，检查核心文件 diff |
| K-04 | 切换运行实例不丢失会话身份和已提交历史 | 验证正常换实例、构建失败回退、Abort 后继续三种轨迹 |
| K-05 | 同一 Session 不会有两个顶层任务同时写历史；消息和工具结果可追溯 | 并发输入、任务取消和扩展重载的确定性测试；每条结果关联原调用 |

交互验证统一使用最小 Web 页面：通过公开接口提交任务、订阅回复和工具事件、停止任务，并在同一 Session 继续。页面不得绕过接口直接读写内部状态；无头 SDK 测试继续用于验证底座契约。

真实模型的任务成功率、延迟和成本目标在模型及评测集选定后补充；不虚构当前基线。

## 2. 用户体验与功能

### 2.1 用户与核心流程

首要用户是把 Agent 嵌入自己的程序的 Go 开发者；其次是编写工具、skills 和工作流的扩展作者，以及使用编码助手验证底座的开发者。

典型流程：开发者登记能力 → CreateAgentSession 创建绑定工作区的会话运行对象 → 向 AgentSession 提交任务 → 查看流式回复和工具执行 → 完成或停止 → 从 SessionManager 保留的历史继续。需要固定路径时，在对话框选择独立 Workflow Agent，或由主 Agent 委派已装配工作流；需要开放探索时，由主 Agent 决定工具或子 Agent。

| 用户故事 | 需求 | 验收归属 |
| --- | --- | --- |
| 作为应用开发者，我希望直接嵌入或远程调用 Agent，以便接入自己的前端 | SDK 与 HTTP/SSE 调用同一 AgentSession 公开能力；核心不依赖页面或前端框架 | K-01；第 2 章 |
| 作为扩展作者，我希望只实现业务能力，以便复用底座 | 工具、skill、工作流通过明确注册入口装配 | K-03；第 5、8 章及扩展补充篇 |
| 作为编码助手用户，我希望能追问、停止并继续工作 | follow-up、steering、Abort 有不同语义，不隐式互换 | K-04、K-05；第 3 章 |
| 作为长期任务用户，我希望保存、恢复与分叉对话 | 产品 Session 独立持久化，不以 Checkpoint 替代 | 第 9～10 章 |

### 2.2 继承的产品约束

1. DeepAgent 是主执行内核；声明式 Workflow 适配为 `WorkflowAgent`，可作为主 Agent 的子 Agent，也可在对话框中选择后独立执行。不提供第三种 workflow-as-tool 产品入口。
2. 会话调度使用 Eino TurnLoop；不自写一套 `Runner.Run` 轮询循环替代它。
3. 普通忙时输入为当前 Trace 的 follow-up，由外层在内层自然停下后消费；steering 在轮次边界消费，两者均不新建 Trace，也不用 preempt 冒充。
4. 扩展变更在随后独立输入受理时选定；已受理 Trace（含 queued/hold）的工具、工作流定义与绑定固定 generation，后续 Turn、follow-up、子调用及恢复不升级，开始执行或继续队列不重新选版或重置总预算。
5. 产品消息允许扩展；模型输入通过投影得到；未知扩展消息的原始数据可保留。
6. 一期支持已编译 Go 包登记，以及加载声明式工作流定义（先兼容指定 Coze Canvas 子集）；不做 Go `.so` 或可视化编排界面。新增节点执行器代码仍需重新构建。
7. 子 Agent 采用开发者代码扩展：自行创建符合接口的实例，通过 ExtensionRegistry 的 `AddSubAgent` 登记，再传入 CreateAgentSession 装配。运行期间的新注册结果由 AgentSession 按既定边界激活。执行限制提供代码默认策略，终端用户无需配置。
8. 模型消息统一采用 `*schema.AgenticMessage` / `model.AgenticModel`；内部消息借鉴 pi 的三类标准职责和可扩展 AgentMessage，先 transformContext，再 convertToLlm。
9. 创建产品 Session 必须显式绑定工作区；默认具备文件、命令、TODO 与通用子 Agent，裁剪由开发者明确指定。
10. 核心概念为 Session → Trace → Turn：Trace 是一次完整运行/回复过程，以 agent_start/agent_end 表达内部循环边界，以 trace.settled 表达产品最终收尾；Turn 是一次模型调用及其工具执行。traceId 关联状态和恢复，观测日志只是附属信息。

### 2.3 范围与非目标

本套 PRD 的完整目标包含：执行循环、模型接入、工具、消息与事件、上下文、压缩、会话，以及 skills / 插件 / 工作流扩展。当前先明确完整行为和系统衔接；交付阶段与开发顺序在全部章节评审后决定。

底座负责前端接入契约，包括调用操作、状态查询、事件流与交互结果回传。建议首先通过 HTTP/SSE 支撑 Web 验证；A2UI 的适配位置预留在对外接入层，是否实现及协议版本随后按场景决定。HTTP/SSE 承担请求和事件传输，A2UI 承担 UI 描述语义，不将三者视为互相替代的同类接口。

前端框架、组件、布局和正式 UI 产品设计不在范围内；最小 Web 页面仅作为测试工具，随已交付的底座能力增加测试控件。CLI 不再是首期必须交付项。

暂不纳入：MCP 市场、分布式多租户调度、公司级审批 BPM、任意 Go 源码文件的进程内热编译加载、对 pi API/会话格式的完全兼容。

本目录不继承相邻 `PRD-pi-desktop-agent.md` 的 Electron 产品范围；那是另一条使用 Pi SDK 的方案。

## 3. AI 系统需求

### 3.1 模型、工具与能力

- 模型经 Eino / eino-ext 接入，按 pi 的思路提供多供应商请求/响应统一、工具及推理回放、缓存策略和用量归一化；现成组件能力直接复用，缺失处补适配。第 4 章给出协议及缓存矩阵，第 8 章负责稳定前缀；全环境目标和具体认证范围沿用既定约束。
- 编码能力作为首个可装配的能力组合；文件和命令执行能力不能成为所有 Agent 场景的隐式前提。
- 业务 Workflow 必须声明输入和输出；用户选择独立 Workflow Agent 后不得先调用主模型来选择路由。
- skills 是按需使用的指令与资源，不等于可执行插件；加载 skill 不自动授予未配置的工具权限。
- 产品 Session 必须绑定工作区。默认装配 DeepAgent 基础能力：文件读写/搜索、命令执行、TODO 与 general-purpose 子 Agent；创建入口负责提供并校验后端及安全策略，开发者可显式裁剪/替换。提示词反映实际能力并可由应用覆盖，装配不等于执行授权。

### 3.2 评估策略

确定性测试负责验证底座行为：假模型产生可预测的工具调用、错误和分块输出，工具使用临时目录或内存替身。真实模型评估负责验证任务效果，两类结果分别记录。

建立小型固定任务集：解释示例代码、完成限定修改并运行测试、调用自定义非编码工具、以两种使用方式运行声明式工作流、加载 skill 后执行任务、在长会话中继续任务。每个用例记录模型配置、输入、期望产物、验收条件和实际事件。任务成功以产物及可重复验证的结果为准，不以模型自述“完成”为准。

## 4. 技术规格

### 4.1 所有权边界

| 对象 | 谁负责 | 关键边界 |
| --- | --- | --- |
| 初次创建与依赖装配 | CreateAgentSession | 返回可用 AgentSession，不持续接管任务 |
| Session、cwd、历史树与分支记录 | SessionManager | 数据不随 Agent/TurnLoop 实例销毁；持久化通过后端完成 |
| Trace 与输入队列、能力版本选择 | AgentSession | 同一 Session 至多一个活动/待恢复顶层 Trace；协调 Agent 执行和 SessionManager 提交 |
| 调度与模型/工具执行机制 | Agent 的 Eino 适配 / DeepAgent / TurnLoop | 消费注入的执行策略，不导入应用层对象 |
| skills、项目指令及扩展来源的读取 | ResourceLoader | 返回候选资源，不改变活动 Trace |
| 工具、子 Agent、工作流等注册定义 | ExtensionRegistry | 生成候选版本，由 AgentSession 决定激活时机 |
| HTTP/SSE、可选 A2UI 映射 | 对外接入层 | 适配应用能力与事件，不拥有会话真相 |
| 最小 Web 测试页面 | 底座之外的测试客户端 | 仅通过公开接口验证已实现的能力 |

核心分三层：模型能力层复用 Eino/eino-ext；通用 Agent 层提供执行、消息和事件契约；应用会话层组合 AgentSession、SessionManager、ResourceLoader、ExtensionRegistry 与策略。对外接入位于最外侧。依赖统一由上层指向下层，详见[第 2 章的分层与依赖规则](02-architecture-boundaries.md#21-三层核心与对外接入)。

**对原方案的源码复核结果**见[差异记录](source-evidence.md#原方案需要修订或补足的地方)：

- 一个 Session 同时最多一个活动 TurnLoop，但整个 Session 生命周期可以先后拥有多个 TurnLoop 实例。`Stop()` 后要重新建立执行循环，不能再次启动旧实例。
- 热重建失败时，AgentSession 协调 Agent 的构建错误与旧版本回退；让 `PrepareAgent` 返回错误会结束当前 TurnLoop。
- 中断任务恢复属于原任务的继续，不是允许任意更换工具拓扑的新任务；恢复与热重建必须协调。
- 已确认采用 `*schema.AgenticMessage`，主/子 Agent 和执行器统一使用匹配的泛型路径。不能以旧注释认定取消/重试缺失，也不能以实现存在替代供应商和恢复兼容性验证。

### 4.2 集成与安全边界

Go SDK 通过稳定的 Session / 任务 / 消息 / 事件概念对接应用，Eino 配置集中在运行时装配处。Go 包的最终导出签名留待相应章节，避免现在冻结未经验证的接口。

工具设计吸收 pi 的分层、五步处理、错误反馈和 Operations。安全按用户要求：策略、审批和审核参考 DSH，原生三平台沙箱参考 Zero 并适配。按调用解析文件效果策略，一次批准与审计独立于执行沙箱，后端缺失不裸跑，full/partial 如实上报；默认已确认为 workspace-write + ask，Auto review 关闭；partial 满足运行数据保护等必需条件后可用并如实标识。详情见 M05 与安全补充篇。模式不隐含网络/读取/任意 Go 插件隔离，凭据不进入普通历史。
