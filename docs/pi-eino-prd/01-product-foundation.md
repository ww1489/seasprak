# 第 1 章：定位、原则与验收目标

状态：讨论稿。对应教程 [M01 开篇](https://dg-ai-notes.pages.dev/modules/ch01-overview)。产品定位、必需工作区、默认基础能力、前端边界及 Web 测试方式已确认；接口细节和阶段切分留开发方案。

## 1. 执行摘要

### 1.1 本章要解决的问题

“用 Eino 重写自己的 Agent”容易演变为两种失控：把 pi 的所有产品功能搬过来，或把 Eino 的所有组件都包装一遍。我们需要先明确：底座服务哪些使用者、哪些行为必须稳定、什么能力允许由应用选择。

**已确认定位：一套可嵌入的通用 Go Agent 底座，L3 提供同级的 `seasprak-code-agent` 与 `seasprak-workflow-agent`，以编码助手验证第一条真实任务链路。** L1 为 `internal/llm`，L2 为 `internal/agent`（含 eino/tools，`Agent` 不改名）；L3 的 `internal/codeagent`（原 sessions）和 `internal/workflowagent` 已独立接入源码，复用中立 `internal/storage`；两类工厂与 Web 资源有对应默认测试，最终认证见 [P3 验证记录](../p3-verification.md)。通用性通过非编码工具和独立工作流的客观验收证明，不通过增加专用跨 Agent 框架证明。

### 1.2 从 pi 借鉴的原则

| 原则 | pi 依据 | 本产品要求 |
| --- | --- | --- |
| 组合优先 | coding-agent SDK 装配模型、工具、资源与会话；见证据 P-02 | SDK 暴露底座能力，对外接入层复用它服务不同前端 |
| 核心行为与具体能力分开 | 低层 Agent 的工具通过接口提供；见 P-03 | Agent 执行路径不按某个业务工具名写特殊分支 |
| 产品消息不等于模型消息 | AgentMessage 扩展、上下文变换和模型转换；见 P-04 | 历史、显示与模型输入分别定义 |
| 扩展有明确入口 | 工具、命令、事件、渲染注册；见 P-05 | 新能力通过注册和生命周期进入系统 |
| 分层可组合 | 依赖允许指向更底层的公共类型；见 P-01 | L1 模型、L2 通用 Agent、L3 同级 Code/Workflow 分别组合；两类互不导入，下层不依赖上层 |

上述事实的源码链接、行号与版本见[证据索引](source-evidence.md)。它们是选择原则的依据，不意味着要复制 TypeScript 类型机制、TUI 或 pi 的完整兼容性。

### 1.3 最小化如何落实

每项内置能力都要回答：哪个已确认场景需要它？是否能由可选扩展承载？关闭它后哪些验收会失败？没有当前用途的配置、接口与包不先建。

已确认：Code Agent Session 必须绑定工作区；默认保留 DeepAgent 的文件读写/搜索、命令执行、TODO 与 general-purpose 子 Agent。Workflow 不继承这套默认装配或会话权限，由自身定义明确输入、资源与策略。创建入口负责提供相应后端及安全策略，不让使用者逐项拼装基础能力。开发者可在代码中显式裁剪或替换，不能因默认后端缺失而静默裁剪后宣称装配成功。基础提示词说明实际能力与使用边界，可由应用替换，不强制具体业务人设。

## 2. 用户体验与功能

### 2.1 底座使用者：嵌入自己的应用

**US-01**：作为应用开发者，我希望通过 Go SDK 或对外接口创建会话、提交任务和接收事件，从而让自己的应用或前端使用同一套 Agent。

正常轨迹：业务登记 Code Agent 能力并提供模型 → CreateAgentSession/OpenAgentSession 取得 AgentSession → 提交输入 → Agent 执行 → SessionManager 保存结果 → 获取事件与状态 → 在同一 Code Agent 会话继续。Workflow 则由业务调用独立的 Workflow 创建/打开目标入口，使用自己的节点状态和生命周期；两类互调只由业务通过已有受控工具接口组合。

验收条件：

- **FR-01**：显式提供测试工作区，以假模型和受控工具替身在无 stdin、无 TTY 的进程内完成一次工具往返。
- **FR-02**：每个任务有可关联到 Session 的身份；最终状态至少区分完成、失败、已取消；等待用户输入另有明确状态。
- **FR-03**：SDK 不强制输出到 stdout；默认基础能力及必需后端在装配时校验，缺失则明确报错。开发者显式裁剪后只校验保留的能力，裁剪不取消 Session 的工作区绑定。
- **FR-04**：缺少模型、无效能力定义等装配错误在执行前报告，附可定位的原因。

### 2.2 首个验证者：编码助手用户

**US-02**：作为开发者，我希望 Agent 能在明确工作区中阅读、修改文件并运行测试，且结果可以检查。

正常轨迹：用户给出示例仓库与限定改动 → Agent 阅读 → 修改允许的文件 → 执行指定测试 → 报告改动及测试结果。

验收条件：

- **FR-05**：默认装配及首个编码示例均具备文件读写/搜索、命令执行、TODO 和通用子 Agent；验证实际调用而非仅列出名称。具体工具名和复用实现由第 5 章确定。
- **FR-06**：测试命令失败时，报告中保留真实退出状态，不能仅凭最终文本声称成功。
- **FR-07**：每次工具执行能追溯到任务、工具名、输入和结果；展示与持久化的敏感字段处理由第 7、10 章规定。
- **FR-08**：停止任务后 Session 和已提交历史仍在，后续输入可开启新任务；不得要求用户重启整个产品进程。

异常轨迹：用户在模型流式输出或工具执行期间停止 → 底座报告取消结果 → 保留已发生的副作用与历史 → 同一 Session 接受下一任务。取消不能承诺撤销已经写入的文件或已完成的外部操作。

### 2.3 扩展作者：增加能力

**US-03**：作为扩展作者，我希望增加一个业务工具、一份 skill 或一条声明式工作流，不必修改任务循环。

验收条件：

- **FR-09**：分别提供 Code Agent 工具、skill 与独立 Workflow 的最小示例，按各自阶段完成可验证任务；不改 L2 执行循环，不将 Workflow 登记为内置子 Agent。
- **FR-10**：业务直接调用独立 Workflow 的目标入口，只执行工作流及其声明节点；Code Agent 主模型选路调用为 0，不经 AgentSession/targetAgent 执行。新 Workflow API 已接入唯一 SDK 入口，有对应默认测试及消费者，最终认证见验证记录。
- **FR-11**：各自运行固定原能力版本，不因另一类更新而升级；后续独立运行按自身受理边界选择版本，事件说明实际版本。动态加载、热重载和多 generation 保留原未来阶段。
- **FR-12**：各类自身加载或构建失败不会混合新旧能力；按原回退策略处理，另一类的版本、审批或恢复不能代替本运行条件。

### 2.4 前端接入与 Web 验证

**US-04**：作为接入底座的开发者，我希望用一个简单 Web 页面验证 Agent 行为，再把同样的接口交给实际产品前端。

已确认：本产品定义底座对外暴露什么，不规定前端如何实现。Web 页面是测试客户端；它使用公开接口，不承载 Agent 循环、会话持久化或扩展装配逻辑。

验收条件：

- **FR-13**：已交付的 Code Agent 会话创建、任务提交、状态查询和取消能力均有对外入口；独立 Workflow 的创建、打开、结构化输入、查询、审批、显式恢复、取消和事件入口已接线，外层分别调用两类独立资源，Workflow 不沿用 AgentSession/targetAgent。两类审批、恢复与事件各按自身身份路由；Coze、动态导入和热重载仍属未来阶段，最终认证见 [P3 验证记录](../p3-verification.md)。
- **FR-14**：Web 页面可订阅文本增量、工具执行、错误及任务状态；事件能关联到 Session 和任务。
- **FR-15**：最小 Web 页面能完成“提交 → 观察执行 → 停止 → 同一会话继续”的测试，不访问后端内部数据文件或全局可变状态。
- **FR-16**：底座和 SDK 可独立构建、测试、使用；移除 Web 页面或更换前端框架，不影响 Agent 的执行行为。

实现建议：先用 HTTP 承载操作与查询、SSE 承载事件；A2UI 等 UI 描述协议在对外接入层映射，按实际场景增加。其版本、消息字段和动作回传契约在第 6～7 章及接入补充篇确定，不提前承诺完整 A2UI 实现。

### 2.5 非目标与待定范围

不复制 pi TUI、npm 包分发、全部模型供应商或内部消息格式，不提供 Go 源码热编译平台，不把工作流做成公司级 BPM。当前不提供可视化编排界面；保留 Workflow 静态定义与现有节点级能力，动态定义、Coze 导入、热重载、多 generation 和补参属于原未来阶段，本轮不启动 P4/P5。

前端框架选型、组件设计、页面布局和正式 UI 产品实现不纳入 PRD。首期交互验证使用最小 Web 页面；CLI 不作为首期必交付项。远程多用户服务仍属于后续范围。

## 3. AI 系统需求

底座提供能力定义、上下文构建、执行与可观察结果；Code Agent 模型在许可能力内决定开放任务动作，普通 general-purpose/专家委派保持父 Trace 权限、预算、generation 与取消约束。固定路径由业务直接调用独立 Workflow，或用已有受控工具组合两类；被调方独立校验与授权，不通过 task/targetAgent 把 Workflow 内置到 Code Agent。

默认基础能力可用于编码及其他工作区任务，不将编码设为唯一业务人设。开发者可通过 CreateAgentSession 显式覆盖系统指令、裁剪工具或加入业务能力；非编码任务也保留工作区绑定。经裁剪后，模型输入只描述仍可用的工具，不提示调用已经关闭的能力。

**验收拆分**：

| 层次 | 检查内容 | 通过条件 |
| --- | --- | --- |
| 底座契约 | 生命周期、工具调用、事件、历史和热换 | 固定输入与可控模型下所有断言通过 |
| 模型效果 | 能否理解任务并得到正确产物 | 对选定模型运行版本化任务集，按产物逐项判定 |
| 可扩展性 | 扩展是否要求侵入核心 | 新示例只新增扩展和装配代码，不改执行循环 |
| 前端接入 | 对外操作和事件能否支撑真实交互 | 最小 Web 页面完成 FR-13～FR-16，且没有绕过接口 |

暂不设未经测量的 token 成本、延迟或跨模型成功率承诺。

## 4. 技术规格

### 4.1 继承与补足

继承独立 Go module、唯一公开 `sdk/sdk.go`、L2 Agentic DeepAgent/TurnLoop，以及 Code Agent 的 AgentSession、SessionManager、资源/登记契约和普通受控委派。Code Agent 与共享存储已位于 `internal/codeagent`、`internal/storage`；同级 `internal/workflowagent` 已独立拥有定义、编译、图、节点状态和生命周期，旧 Code 工作流接线已退出，两类工厂及 Web 三类资源路由和独立视图已接通。共用 `internal/storage` 契约及 jsonl/memory，但不共用写入者、历史、审批、恢复、generation 或隐式预算。完整 ExtensionRegistry/ResourceLoader 仍按原阶段验收，当前普通目标使用 SessionOptions.Agents；真实签名/DTO 见开发 06/10/13。名称与边界见[第 2 章](02-architecture-boundaries.md#23-与-pi-对齐的对象名称与职责)，最终认证见验证记录。

本章的产品约束是无头 SDK、分别暴露两类公开能力、最小 Web 验证、编码及非编码示例、各自版本一致与取消后状态可查。已有单调用校验、冻结参数、票据、预算、真实取消退出和 unknown 核对不弱化；高级跨任务编排/审批/补偿、业务幂等、完整持久子树恢复与跨运行总预算由业务负责。旧开发数据本次不迁移、不自动删除。

### 4.2 一期插件语义

“同进程 Go 插件”指被编译进应用并通过注册入口装配的 Go 包。已编译能力静态装配保留；运行时启停、skill/配置重读及安全边界重建 Agent 的需求仍由原未来阶段实现，本次不启动热重载或 P4/P5，也不将规格描述为已交付。

修改 Go 源码或安装一个此前未编译的新 Go 包，需要重新构建程序。这与 skills 文本资源的重载不同。若以后要运行时引入新代码，再单独评估进程外协议或其他运行环境。

### 4.3 数据与权限

工作区为所有 Code Agent Session 的必需绑定，由应用在创建时显式提供并验证其执行环境、真实路径和访问范围；缺失时拒绝创建，不隐式使用进程 cwd。SessionManager 的存储位置与业务工作区分开管理；凭据不进入普通对话历史，同进程插件视作信任代码。安全参考已按用户要求采用双来源：DeepSeek Harness 负责策略/审批/审核职责，Zero 负责 Go 原生三平台沙箱实现。独立审批、按调用解析策略及必要审计保留；默认组合已确认为 workspace-write + ask，Auto 默认关闭；实际限制见[安全补充篇](12-security-sandbox.md)，不套用 pi 的默认许可行为，也不采用 Zero 的 auto degraded 裸跑。
